# Deploy lento e sem espaço — 26/10/2026

Fonte: log anexado em [talk-ia.md](../talk-ia.md), referente ao push `af63b9b` do Expert. O workflow terminou com `write /tmp/.tmp-compose-build-metadataFile-...: no space left on device` após 39 minutos. O erro é de capacidade do disco do servidor durante o build do Docker, não uma falha de compilação do Next. O checkout do servidor já havia sido atualizado para `af63b9b`, mas o `docker compose up` não chegou à etapa de recriar os containers; por isso o novo código não deve ser presumido em produção.

Os tempos elevados de cópia/exportação são compatíveis com pressão de disco ou I/O, mas não provam CPU, RAM ou tipo de armazenamento sem métricas do servidor.

## Correção enviada ao `main` do Expert (`6545a07`)

- `web/next.config.mjs` ativa `output: "standalone"`; o Dockerfile copia só o servidor rastreado pelo Next, arquivos estáticos e `public`, sem levar o aplicativo inteiro nem executar `npm prune` na imagem final. O [Next.js 14 documenta esse formato](https://nextjs.org/docs/14/pages/api-reference/next-config-js/output).
- O workflow verifica espaço antes do build. Se houver menos de 3 GB livres em `/tmp` ou no disco do Docker, remove imagens pendentes e cache não usado, preservando até 1 GB primeiro; se ainda faltar espaço, limpa o restante do cache e encerra cedo com diagnóstico.
- `scripts/deploy-prod.sh` compara o commit atual com o último deploy concluído, registrado em `.deploy-successful-sha`. Reconstrói somente web, API ou orquestração que tenham mudado. Não toma uma tentativa fracassada como deploy concluído.
- Depois de subir, remove imagens pendentes e limita o cache de build a 2 GB, em vez de esvaziá-lo em todos os deploys. O [Docker documenta `--keep-storage`](https://docs.docker.com/reference/cli/docker/builder/prune).

No ambiente local, a nova imagem web construiu e respondeu HTTP 200; `docker image ls` mostrou 227 MB contra 859 MB da imagem anterior. Isso valida o empacotamento, **não** a velocidade no servidor. A primeira execução do novo script ainda pode ser lenta porque não há marcador de deploy anterior; as seguintes devem reaproveitar imagens e cache quando os serviços não mudarem.

## Pendência operacional

Conferir `df -h /tmp /var/lib/docker`, `df -i /tmp /var/lib/docker`, `docker system df` e `free -h` no próprio servidor.
