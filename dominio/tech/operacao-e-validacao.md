# Operação e validação

**Referência dos comandos versionados; não indica estado vivo de servidores.** O Expert roda localmente pelo [docker-compose.yml](../../chateau-expert/docker-compose.yml) e define produção em [docker-compose.prod.yml](../../chateau-expert/docker-compose.prod.yml). Ambos usam Caddy, web, API e PostgreSQL. Desde 28/10/2026, `orchestration` é Quarkus nos dois Compose; sobe sempre em produção e, no ambiente local, com o perfil `ia` e o Neo4j de exemplo. Python permanece no perfil `comparacao` em produção ou `ia-python` no ambiente local; não recebe tráfego padrão da API. Sem modelo disponível, a busca usa mock. `ORCHESTRATION_URL` só substitui o endereço interno padrão da orquestração. O Neo4j guarda o grafo e o PostgreSQL guarda o estado da aplicação.

- **Decisões de 10/11/2026:** push no `main` de `chateau-expert` não dispara o workflow. Apenas push na branch `deploy`, que recebe cópias do `main` (`git push origin main:deploy`), executa os testes e, se eles passarem, publica em produção. O [workflow](../../chateau-expert/.github/workflows/deploy.yml) testa backend com PostgreSQL e web, constrói no GitHub Actions três imagens `linux/amd64` (API, web e Quarkus) e publica no GHCR privado com a tag do SHA do commit. O servidor recebe um token temporário para baixar todas as imagens, confere espaço e arquitetura, atualiza o checkout para esse SHA e sobe os containers sem build; `.env.prod` e volumes de PostgreSQL/Neo4j permanecem no servidor. O marcador `.deploy-successful-sha` só é atualizado após o Compose subir. Um deploy por vez. O checkout remoto usa `git reset --hard`; alterações locais lá não são preservadas. Rollback: publicar um commit anterior na `deploy`. O workflow não valida o Data nem as duas implementações da orquestração no mesmo gate. [Contexto e limitações](../../docs/analises/deploy-imagens-2026-11-10.md).
- Testes de integração do backend: `npm --prefix chateau-expert run test` a partir da raiz deste workspace (o script do Expert cria/usa um PostgreSQL de teste em container). Testes unitários/integração usam Vitest; [instruções](../../chateau-expert/backend/scripts/test-integration.sh).
- O Data usa `python3 -m unittest discover -s tests -v` a partir de `chateau-data/scripts`; parte da suíte consulta a API Sucupira e depende da rede. [Guia](../../chateau-data/scripts/tests/README.md). O teste de extração PDF tem [falha confirmada](../dados/fontes-e-pipeline.md).
- A orquestração Python tem testes `pytest`; a Quarkus tem testes Maven com Neo4j de teste via Dev Services. A [comparação](../../chateau-expert/orchestration/README.md) verifica a equivalência do contrato HTTP entre implementações com um servidor simulado do modelo de IA e, quando disponível, o modelo real. A comparação deve acompanhar mudanças em qualquer das duas implementações.
- O schema usado pelo modelo texto→Cypher pode ser comparado com o Arrows e o Neo4j por [comparar_com_modelo.py](../../chateau-expert/orchestration/schema/comparar_com_modelo.py). A extração do schema de produção é um procedimento separado, descrito em [orchestration/schema](../../chateau-expert/orchestration/schema/); não assumir que o arquivo versionado reflita o servidor no momento da tarefa.

Segredos ficam em `.env`/`.env.prod` fora do Git; o [template](../../chateau-expert/.env.example) lista as variáveis. `INTERNAL_API_TOKEN` (mesmo valor para web e API, ≥ 32 caracteres) é obrigatório: sem ele a API encerra na inicialização. Ele precisa existir no `.env.prod` do servidor **antes** do deploy que introduz a autenticação web → API. Nunca registrar valores reais em documentação de domínio.
